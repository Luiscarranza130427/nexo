# Projects

The work an organization delivers, optionally for a client, with a team assigned.

## Model

`Project` (full schema in [DATABASE.md](./DATABASE.md)).

| Field                  | Notes                                                                              |
| ---------------------- | ---------------------------------------------------------------------------------- |
| `code`                 | Generated by the API (`NEX-001`), unique per organization, never reused.           |
| `name`                 | Required, 1–200 characters.                                                        |
| `description`          | Optional, up to 2000 characters.                                                   |
| `clientId`             | Optional. Must belong to the same organization.                                    |
| `status`               | `PLANNING` · `ACTIVE` · `ON_HOLD` · `COMPLETED` · `CANCELLED`. Default `PLANNING`. |
| `priority`             | `LOW` · `MEDIUM` · `HIGH` · `URGENT`. Default `MEDIUM`.                            |
| `startDate`, `dueDate` | Optional calendar dates. `dueDate` ≥ `startDate` when both exist.                  |
| `organizationId`       | Tenant boundary. Never accepted from, nor returned to, the client.                 |

Defaults: a new project has not started (`PLANNING`), and nothing is urgent until
someone says so (`MEDIUM`).

There is no status workflow yet: any allowed role may set any status. No
`completedAt` column was added; nothing needs it today.

## Project codes

Codes come from `Organization.projectCodeSequence`, a per-organization counter.

1. In one transaction, the counter is incremented and the project inserted with
   `NEX-` plus the new value, zero-padded to at least three digits (`NEX-001`,
   `NEX-042`, `NEX-1000`).
2. The increment is an `UPDATE … SET seq = seq + 1`, which takes a row lock. Two
   concurrent creates queue behind each other and always get distinct numbers.
3. The counter never goes down, so deleting `NEX-002` does not free the code:
   the next project is `NEX-003`.
4. A collision is only possible if a code was written outside the API (a manual
   import). The transaction then rolls back — and its increment with it — so the
   counter is advanced past the taken number and the create retried, at most five
   times, before failing with `PROJECT_CODE_GENERATION_FAILED`.

`COUNT(*) + 1` and `MAX(code) + 1` were rejected: the first collides under
concurrency and after deletions, and both reuse the code of a deleted project.

The `NEX` prefix is fixed. Making it configurable per organization is a plausible
future setting and deliberately not built.

Side effect: creating a project touches `Organization.updatedAt`, since the counter
lives on that row. Nothing reads that timestamp today.

## Permissions

| Role      | List | View | Create | Edit | Delete | Manage members |
| --------- | ---- | ---- | ------ | ---- | ------ | -------------- |
| `OWNER`   | ✅   | ✅   | ✅     | ✅   | ✅     | ✅             |
| `ADMIN`   | ✅   | ✅   | ✅     | ✅   | ✅     | ✅             |
| `MANAGER` | ✅   | ✅   | ✅     | ✅   | ❌     | ✅             |
| `MEMBER`  | ✅   | ✅   | ❌     | ❌   | ❌     | ❌             |

Enforced by `@Roles(...)` and re-read from the database on every request. The UI
hides what a role cannot use; that is UX only.

## Tenancy

- The organization always comes from the validated session. `organizationId` and
  `code` are not in any DTO, and `forbidNonWhitelisted` turns an attempt to send
  them into a 400.
- A project of another organization answers **404**, never 403, for every
  endpoint including members.
- `clientId` and `memberId` filters run inside the organization's `WHERE`, so a
  foreign id simply matches nothing.
- Linking a client checks it belongs to the organization (`PROJECT_CLIENT_NOT_FOUND`
  otherwise — the same answer for a foreign client and a non-existent one).
- Assigning a member checks an active membership in the organization.

## Endpoints

| Method   | Path                            | Roles                 | Success |
| -------- | ------------------------------- | --------------------- | ------- |
| `GET`    | `/projects`                     | any member            | 200     |
| `GET`    | `/projects/:id`                 | any member            | 200     |
| `POST`   | `/projects`                     | OWNER, ADMIN, MANAGER | 201     |
| `PATCH`  | `/projects/:id`                 | OWNER, ADMIN, MANAGER | 200     |
| `DELETE` | `/projects/:id`                 | OWNER, ADMIN          | 204     |
| `GET`    | `/projects/:id/members`         | any member            | 200     |
| `POST`   | `/projects/:id/members`         | OWNER, ADMIN, MANAGER | 201     |
| `DELETE` | `/projects/:id/members/:userId` | OWNER, ADMIN, MANAGER | 204     |
| `GET`    | `/organization/members`         | any member            | 200     |

`GET /organization/members` is deliberately minimal: it lists active members of
the caller's organization (`userId`, names, `avatarUrl`, `email`, `role`) so the
members picker has people to offer. Inviting, removing and changing roles belong
to the team module, which is not built yet.

### Filters, sorting and pagination

| Param       | Values                                                                             | Default     |
| ----------- | ---------------------------------------------------------------------------------- | ----------- |
| `page`      | ≥ 1                                                                                | `1`         |
| `limit`     | 1–100                                                                              | `10`        |
| `search`    | matches `name`, `code`, `description`, case-insensitive                            | —           |
| `status`    | a `ProjectStatus`                                                                  | —           |
| `priority`  | a `Priority`                                                                       | —           |
| `clientId`  | UUID                                                                               | —           |
| `memberId`  | UUID — projects where that user is a member                                        | —           |
| `sortBy`    | `name` · `code` · `createdAt` · `updatedAt` · `startDate` · `dueDate` · `priority` | `createdAt` |
| `sortOrder` | `asc` · `desc`                                                                     | `desc`      |

Sort fields are a closed list. Dates sort empty values last in both directions;
priority sorts by severity (`LOW` < `URGENT`); `id` breaks ties so pages never
overlap or skip rows.

### Responses

A list row carries the client reference and **counts** — `membersCount`,
`tasksCount` — from the same query as the rows. No member or task records are
loaded for a list, so there is no N+1.

The detail adds `members` (`userId`, names, `avatarUrl`) and a task summary with
real counts per status (`total`, `todo`, `inProgress`, `inReview`, `done`,
`cancelled`). All zero until tasks exist in phase 8; nothing is invented.

Users are identified by `userId` everywhere in this module, never by a bare `id`,
so they cannot be confused with a project or a membership row.

## Members

- Only an **active** member of the organization can be assigned; anyone else —
  unknown user, other organization, deactivated account — gets
  `PROJECT_MEMBER_NOT_IN_ORGANIZATION`.
- A duplicate assignment is refused by the `(projectId, userId)` unique
  constraint itself (`PROJECT_MEMBER_ALREADY_EXISTS`), so two simultaneous
  requests cannot both succeed.
- Removing a member deletes only the assignment. The user and their membership
  stay.
- Someone deactivated or removed from the organization keeps their assignment
  row but disappears from counts and member lists. Cleaning those rows up is the
  team module's job.

## Delete policy

Only `OWNER` and `ADMIN`. A project **with tasks cannot be deleted**
(`409 PROJECT_HAS_TASKS`): cancelling or completing it is how work is retired.

The "no tasks" condition is part of the `DELETE` statement itself rather than a
separate count, so a task created in between cannot be cascaded away silently.
Assignments go with the project; users, memberships and the code counter do not.

## Dates

Calendar dates are sent as `YYYY-MM-DD`, stored at UTC midnight and returned as
ISO strings. Impossible dates (`2026-02-30`) are rejected by the API and by the
form. `dueDate < startDate` is `INVALID_PROJECT_DATES`; on update the rule is
checked against the merged result, so moving one date must still respect the
other.

The frontend formats these dates **in UTC**. Formatting at local midnight would
show a 1 October due date as 30 September in Lima. No other timezone logic exists.

## Errors

| Code                                 | HTTP | When                                                   |
| ------------------------------------ | ---- | ------------------------------------------------------ |
| `PROJECT_NOT_FOUND`                  | 404  | Unknown id, or a project of another organization.      |
| `PROJECT_CLIENT_NOT_FOUND`           | 400  | The client does not exist in this organization.        |
| `INVALID_PROJECT_DATES`              | 400  | `dueDate` before `startDate`.                          |
| `PROJECT_MEMBER_NOT_IN_ORGANIZATION` | 400  | The user is not an active member of this organization. |
| `PROJECT_MEMBER_ALREADY_EXISTS`      | 409  | Already assigned.                                      |
| `PROJECT_MEMBER_NOT_FOUND`           | 404  | Removing someone who is not assigned.                  |
| `PROJECT_HAS_TASKS`                  | 409  | Deletion refused because the project has tasks.        |
| `PROJECT_CODE_GENERATION_FAILED`     | 500  | Repeated code collisions (manual imports only).        |
| `FORBIDDEN`                          | 403  | Authenticated, but the role is not enough.             |

`null` for a field that cannot be null (`name`, `status`, `priority`) is a 400;
nullable fields accept `null` to clear them. Prisma errors never reach the client.

## Indexes

Migration `add_project_code_sequence` adds the counter and two indexes:

| Index                              | Purpose                                    |
| ---------------------------------- | ------------------------------------------ |
| `[organizationId, createdAt]`      | Default list ordering.                     |
| `[organizationId, dueDate]`        | Sorting by due date; "what is due soon".   |
| `@@unique([organizationId, code])` | Existing. Code uniqueness per tenant.      |
| `[organizationId, status]`         | Existing. Status filter.                   |
| `[clientId]`                       | Existing. Client filter and client detail. |
| `ProjectMember [userId]`           | Existing. `memberId` filter.               |

`priority` is not indexed: four values barely narrow anything the
`organizationId` prefix has not already narrowed.

## Frontend

| Route                 | Purpose                                            |
| --------------------- | -------------------------------------------------- |
| `/projects`           | List with search, filters, sorting and paging      |
| `/projects/new`       | Create — no code field; the API assigns it         |
| `/projects/[id]`      | Detail: summary, client, dates, team, task summary |
| `/projects/[id]/edit` | Edit                                               |

Lives in `src/features/projects/` (`api/`, `components/`, `hooks/`, `schemas/`).

- **URL is the state**: `page`, `search`, `status`, `priority`, `clientId`,
  `sortBy`, `sortOrder`. Changing a filter or the order resets the page.
- One sort control (a select) rather than clickable headers, so sorting works the
  same on a phone as on a desktop.
- The client filter and the form's client picker reuse the clients module's own
  query, capped at the API maximum of 100 sorted by name. A larger client base
  will need a searchable picker.
- Desktop renders a table; below `md`, compact cards.
- Status and priority badges always carry text; priority also carries an icon.
- Due dates show "Vence hoy", "Vence en N días" or "Vencido" — display only, and
  nothing for completed or cancelled projects.
- Members are managed in a dialog, from the detail page or the list row menu. It
  searches existing organization members only; nobody is created or invited.
- The breadcrumb labels a project by its code: `Proyectos › NEX-001 › Editar`.
- There are no summary counters above the list: showing real ones would take four
  extra requests per page load or a statistics endpoint, which belongs with
  dashboard analytics rather than here.

Query keys: `projectKeys.lists()`, `.list(filters)`, `.detail(id)`,
`.members(id)`. A create invalidates lists; an edit refreshes the detail and
lists; a membership change invalidates members, detail and lists — never a
blanket `invalidateQueries()`.
